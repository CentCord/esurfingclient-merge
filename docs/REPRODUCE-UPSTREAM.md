# 复现上游多拨故障（2026-10-26 凌晨实验室）

> 目的：在没有真实校园网的情况下，用协议 mock + OpenWrt 虚拟机，复现"一个账号的线路出问题，
> 全部账号跟着退登重登"的现象，并对比修复后的行为。

## 一、实验环境

```
宿主机 macOS（QEMU hvf）
   ├── mock A：scenario=portal_redirect_all  →  127.0.0.1:8081（代表"会话已死的线"）
   └── mock B：scenario=normal               →  127.0.0.1:8082（代表"正常的线"）

VM：OpenWrt 24.10.4 armsr/armv8（aarch64_generic）
   dummy0(10.99.0.1) + wan2_dev(10.99.0.2) + wan3_dev(10.99.0.3) + wan4_dev(10.99.0.4)
   4 个假账号 u1..u4，mark 分别为 0x100 / 0x200 / 0x300 / 0x400
```

分流方式（关键）：QEMU user-mode 下宿主机看不到 guest 源 IP，所以在 VM 内部用 nftables
**按 mark** 把探测/认证流量 DNAT 到不同宿主端口：

```
meta mark 0x000（未标记）      → 10.0.2.2:8081（死线）
meta mark 0x100                → 10.0.2.2:8081（死线）
meta mark 0x200-0x400          → 10.0.2.2:8082（正常线）
```

所有路由表统一走 eth0，postrouting 对 10.99.0.0/24 做 masquerade，保证 DNAT 后的包能经 QEMU NAT 到达宿主机。

## 二、对照组（上游 8489c9d）

30 秒内，4 个账号的探测分布与状态：

| 指标 | 数值 |
|---|---|
| 死线 mock（8081）收到的探测 | **68** |
| 正常线 mock（8082）收到的探测 | **3** |
| auth#2 登录 / 登出 | **8 / 7** |
| auth#3 登录 / 登出 | **8 / 7** |
| auth#4 登录 / 登出 | **8 / 7** |
| 三个账号首次"需要认证"时刻 | **18:08:34（同一秒）** |

**96% 的探测流量打到了死线**——因为探测没绑 mark，全部走主路由表。

## 三、实验组（当前代码）

同样的场景与账号：

| 指标 | 数值 |
|---|---|
| 死线 mock（8081）收到的探测 | 33（约 1/4，只有账号1） |
| 正常线 mock（8082）收到的探测 | 386（302 未认证 55 + 204 已认证 331） |
| auth#2 登录 / 登出 | 0 / 0 |
| auth#3 登录 / 登出 | 1 / 1 |
| auth#4 登录 / 登出 | 1 / 1 |

探测按 mark 分流，只有账号1 的线路被判定异常，其它账号不再跟着重登。

## 四、结论

1. **上游的探测不绑 mark，导致 96% 的探测流量反映的是主线路状态。**
   主线路会话一死，所有账号同时看到 302，同时退登重登——本实验在 30 秒内复现出
   "3 个账号各 8 次登录、7 次登出、同一秒翻转"。
2. **修复后探测按 mark 分流**，只有对应线路的账号受影响。
3. 同一秒翻转是"共享观察值"的直接后果，不是巧合。

## 五、限制（必须说明）

- mock 的 keep 响应与真实服务端不完全一致，实验组里 auth#3/#4 各有 1 次心跳失败后登出；
  数量级上的差异（8/7 vs 1/1）仍足以说明问题。
- 这是模拟环境，不代表真实校园网的全部行为；真实环境的"被踢"仍可能由服务端策略触发。
- 实验只使用假账号 u1..u4，未接触真实校园网账号与真路由器。
